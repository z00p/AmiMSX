## Space Manbow (R2K_SpaceManbow, KonamiSCC)

**Symptom.** In AmiMSX the rocky ground strip at the bottom is a dark blue band, and many enemies are missing.

**openMSX, during play (36 s):**
- About 4 lines after the VBlank interrupt the game switches to SCREEN 5 (R#0 = 16h), with page R#2 = 3Fh and R#23 = C0h.
- At about line 80 after VBlank, just before the display, it returns to SCREEN 4 (R#0 = 04h/14h) with:
  - R#23 = 24h (vertical scroll by 36 lines);
  - R#18 = 0Ch;
  - R#2 = 30h or 31h (name table at C000h or C400h, two 1 KB tables);
  - a line interrupt in R#19.
- At that interrupt, R#5 (sprite attribute table) changes mid-screen: E7h→EFh or F7h→FFh, alternating per frame.
- R#9 = 80h: 212 lines.
- No VDP commands are used. VRAM is written by the CPU (36-915 bytes a frame through port 98h, R#14 = 3).

**Ground strip.** With 212 lines and R#23 = 24h, display lines 220-255 of the 256-line name space come from name-table rows 24-31. That's why the game uses 1 KB name tables, not 768 bytes. AmiMSX's SCREEN 2/4 tile pass covers `32*24` names (PREPRUT1, COPYBUF and others), so rows 24-31 are never drawn: the empty band.
- **What it really was (3 Oct 2026):** AmiMSX's VRAM has rows 24-31 (rendered with tools/render_scr4_full.py), and the SCREEN 4 tile pass covers 32 rows. The R#2 change at line 81 (status page 3Fh to name table 30h/31h) is a table split, so the playfield (lines 81-211) is drawn line by line by HUDSplit4 into SCREENB, which stopped at line 192. Lines 192-211 showed the backdrop. Fixed: HUDSplit4 runs to line 212 in 212-line mode.
- **Fix:** in SCREEN 4 (and SCREEN 2 on the V9938) with 212 lines or a non-zero R#23, render 32 name rows and wrap the vertical scroll at 256 lines, not 192. Also the G3 pattern/colour tables: rows 24-31 use the fourth table block, masked by R#4/R#3 like the other three.

**Enemies.** AmiMSX supports a mid-frame sprite table switch (R#5/R#6) only for sprite mode 1. The snapshots and the two-pass IMPSPR read mode-1 tables; IMPSPR2 (mode 2) reads one table for the whole frame. Space Manbow draws its sprites from two attribute tables, one above the split and one below, so one set is lost.
- **Evidence (openMSX, 36 s):** four attribute tables in use (R#5 = E7h/EFh and F7h/FFh, a pair per frame). The table used above the split holds the sprites at Y = 80-150, the one below holds Y = 170-204; unused sprites sit at Y = 40. A renderer using one table per frame draws one half's enemies only.
- **Fix:** extend the mode-1 split to IMPSPR2: snapshot the mode-2 attribute and colour tables at the R#5 change line, and draw two passes (or bands) split at that line.

## Jailbreak (M_Jailbreak_Kon, Konami)

**Symptom.** In play, rows of the wrong scenery flash at the top of the playfield (the 60 s capture varies from run to run).

**openMSX:**
- SCREEN 5, 212 lines (R#9 = 82h).
- Each frame, at line interrupts, it flips between page 1 scrolled (R#2 = 3Fh, R#23 = 82h) and page 0 unscrolled (R#2 = 1Fh, R#23 = 0) for the HUD.
- The map scrolls with HMMM copies and an LMMM with TIMP.

**Theory (superseded 15 Oct).** The handler this theory named, VDP17m5, was never installed: SCREEN 5 uses VDP17, which records R#2/R#23 writes as events at the MSX line, and ActCopperLine builds them into the per-line copper list, which the copper runs from the next frame start. See `Docs/bitmap_line_events.md` for what is still beam-dependent (the list rebuilt in place on a late frame) and the draft fix.
- **Confirm:** log the MSX line of each R#23/R#2 write (CurLine) next to the Amiga line used. They will differ, and the difference will vary.
- **Fix:** handle bitmap-mode R#23 and R#2 splits like the mid-frame palette and mode splits: record them as events at the emulated MSX line (TabRasCMDS) and build the copper split from those. That's deterministic, and it doesn't busy-wait on the beam (which also costs time).

## Uridium 2 (M_Uridium2_SCC, KonamiSCC): fixed 3 Oct 2026

**Symptom.** The player ship, and at times every sprite, missing for seconds at a time, in both sprite settings. openMSX only hides the ship during the death sequence.

**openMSX:**
- SCREEN 8, 192 lines, horizontal scroll by R#18 plus HMMM copies.
- R#5 alternates between FFh and F7h every frame, in VBlank: two sprite attribute tables, shown on alternate frames.
- HUD split by line interrupt (R#19 = A7h, display line 167): R#2 = 1Fh, R#23 = 0Ah, R#18 = 00h and R#8 = 2Ah (sprites off). The VBlank handler restores the playfield values.

**Cause (AmiMSX event ring, trace-lite build frozen at 39 s).** On frames where the playfield page is also 1Fh, the line-167 R#2 write changes nothing, so no table split was recorded. MIDSAMPLE then kept sampling and took the HUD's R#8 = 2Ah as the playfield's (TopR8 = 2Ah every frame). The overlay counted down and turned off, and R#18 was sampled as the HUD's 00h as well.

**Fix: register-split segments.**
- **Segments:** a change of R#8, R#18 or R#23 on display lines 16-191 (RSPLITCHK) ends a segment. Lines 0-15 count as the frame's own setup, and there are no segments after a table split.
- **Choice:** at line 192 (SEGCLOSE, before the render), the longest segment's MIDSAMPLE values are used.
- **Why not simply stop at the first change:** that broke Bun-Ga-Rua. It turns sprites off above line 79 and on below for its play area, so stopping at the first change kept the sprites-off top, and the heroine vanished.
- **Results:**
  - Uridium 2: with sprites every frame, the 30-57 s film shows the ship and enemies in every capture except the death explosion.
  - Regression (split titles): Uridium 2 at 60 s shows the ship and Nemesis 3 at 45 s shows enemies, both missing in the baselines. Bun-Ga-Rua is unchanged.
  - Chikubi Ninja: the enemies moved a few pixels against the scenery (game state unchanged: 45 s identical, and each capture is its own run). It writes R#18 = F9h/FAh (fine X scroll) for the play area and 00h at line 160 for its panel. The old sample (line 176) took 00h, so sprites ignored the play area's fine scroll, and R#18 moves sprites with the background on the VDP. Now correct; baselines accepted for Chikubi Ninja, Uridium 2 and Nemesis 3.
  - Jailbreak at 60 s: a one-line strip under the orange blocks differs. That's where its known split-timing problem is, so the baseline is kept until the Jailbreak fix.

**Still to check.** "2 frames" mode always draws one of the two alternating tables. Film it for the A1200 preset.

## Zanac EX: title shows the graphics pages (fixed 3 Oct 2026)

**Symptom.** From about 6 to 14 s AmiMSX showed VRAM page 1 (the game's graphics sheets), with sprites off, instead of the title being built on page 0. openMSX keeps the display blanked while it builds, then shows the title.

**Cause** (event ring and a full trace frozen on the R#2 = 3Fh write):
- During the title the game sets R#23 = 30h with R#19 = 0, so the line-interrupt line is (0 - 30h) & 255 = 208, with line interrupts off (IE1 = 0).
- AmiMSX raised FH (S#1 bit 0) at line 208 anyway and held it for 7 lines.
- The VBlank interrupt at line 212 found FH set, so the game's handler (4BEEh, bank 14) took its line-interrupt path. With VR (S#2 bit 6) set, that path selects page 1 (R#2 = 3Fh), R#23 = D8h, R#19 = E4h and sprites off.

**Fix.** With IE1 off, InterHor shows FH only during the matching line (cleared at the next line). With IE1 on, nothing changed: FH stays up to 7 lines or until read, and requests the interrupt.
- openMSX does the same, measured with a probe on status reads. Zanac's handler reads S#1 = 00h after a match at line ~208.
- Jailbreak sets R#19 and then polls FH with IE1 off (4350h: `IN A,(99h) / RRCA / JR NC`). A first fix that never raised FH with IE1 off left Jailbreak on a black screen.
- Zanac's title and its GAME START menu now match openMSX.

**Also seen.** The VR timing in IVDP2 uses only the line's low byte, so lines 256-312 (still in VBlank) report VR clear. It is not involved here, but needs fixing (see Other open items).

## Debug builds hanging at boot: fixed 3 Oct 2026

TRACE and PERFSUBS builds hung on a blue screen from 1863a1f on, and so did a release build with 4 bytes added at the wrong place.
- **Found by** an exception catcher (`-DEXCCHK`): a Line-F exception at the second word of `MOVE.L #OUT98M,DREGOUT98(A3)`.
- **Cause.** The instruction is skipped with `BNE.S *+10` (added in 1ee3275), which assumes it is 8 bytes. DREGOUT98 is OUTS - REGS: once that passes -32 KB, vasm encodes a 32-bit displacement, the MOVE grows to 12 bytes, and the branch lands on $FFFF.
- **Fix.** The three skips (and two safe `BLS.S *+8`) now use labels. `build.sh` refuses `B.. *+n` branches.
- **Debug tools added:**
  - `TRACELITE` (event ring only, full speed);
  - `CORRCHK` (code addresses in the page tables);
  - `HANGCHK` (VBlank watchdog);
  - `EXCCHK` (exception catcher, PC into the ring).
  - The ring now wraps before TrvRegs, which TraceFreeze overwrites.

## MSX Unleashed (R2_Unleashed, Konami)

**Symptom.** It runs into the credits scroller, then fills the screen with "Internal error in ..." by 65 s.

**openMSX.** Runs (dvik & joyrex logo, then the title). Mapper: openMSX's database says Konami (no SCC); AmiMSX's guess agrees.

**Theory.** "Internal error in <line>" is MSX-BASIC's error 51 message, not the demo's. The Z80 has left the demo and ended up in BASIC's error handler, so this is a CPU-level fault. Candidates:
1. The POP/RET 256-byte page-crossing bug fixed in 1863a1f (scrollers often read data with `LD SP,src / POP`). This is the most likely.
2. Undocumented instructions (IXH/IXL, SLL, OUT (C),0).
3. The H and N flags, which AmiMSX doesn't model (DAA after an operation it doesn't track).
- **Confirm:** run the current build to 70 s; if it still fails, use a TRACE build with TRACEFR around the crash to get the last Z80 instructions.

## Snake and Rhino in the Sketch (041)

**Page turns (symptom).** On the 2nd/3rd book page, AmiMSX shows half-updated tiles. openMSX is clean.

**Page turns (theory).** The SCREEN 2 tile cache has two banks, one per table set (added for Uridium). If the game updates the tables of the set that isn't shown and then switches R#3/R#4, the bank's dirty flags must cover those writes. A path that marks only TAB98 (or clears flags before every block is redrawn) would leave half-updated tiles. Low confidence: needs a VDP log across a page turn and an AmiMSX dump of the tile cache.

**Colours.** openMSX shows grey paper with grey rule lines; AmiMSX shows white paper with cyan lines. In openMSX the game writes a full 16-colour palette through port 9Ah at 4.3 s, and again later (65 writes after start-up), so it recolours SCREEN 2 on an MSX2. AmiMSX's palette handler (OUT9Ab) updates COLORMSX2 and the colour registers in every mode, and mode changes don't reset the palette. So the likely cause is that the game never writes the palette in AmiMSX, because it finds an MSX1 there (the machine type in the harness prefs, or how the game detects an MSX2).
- **Confirm:** check MSX2Pal in an AmiMSX PERF dump after 5 s, and AmiMSX's machine type for this run.

## Run-to-run variation (full run, 3 Oct 2026)

52 of 66 titles were pixel-identical across two runs. The ones that varied: Bomb Jack, Zanac, Zanac Ex, Zanac Ex Enhanced, Triton, Alien Attack, Universe Unknown, Bit Logic, Knight Lore, Sacred Valley, Bold, Invasion and io.

**Cause found:** AmiMSX's `LD A,R` returned the Amiga's horizontal beam position (`$DFF007`), so every game that seeds randomness from the R register ran differently on each run. R is now derived from the emulated time (line, cycles left in it, frame counter). Re-calibrated with that build (89427e6): 12 of the 13 are now pixel-identical across runs, including the Zanac family, Bomb Jack and Triton.

**Disk demos failing together (4 Oct 2026): fixed 10 Oct.** In the overnight run and two re-runs the same night, bold, invasion, io and akin2 failed: the MSX-DOS prompt, a blank screen or no capture. On 10 Oct the byte-identical binary passed, and the disk images were unchanged, so it wasn't the code.
- **Not the emulated disk reads:** a DSKIO read on the MVD drive copies from the image in RAM (DIRVD0), with no host I/O and no emulated time.
- **The weak point was loading the image:** the 720 KB read in LOADVD never checked its result, and AmigaDOS Read may return less than asked or fail. A short read left the rest of the image empty, so DOS booted but couldn't load the demo, which matches the symptoms.
- **Fix:** READFILE now reads until all bytes are in (or end of file or an error) and reports a short read. The disk loader treats a short read as an error ("File read error: aborted.") and leaves the drive empty.
- **After the fix:** all five disk demos match their baselines at every capture (10 Oct). The 4 Oct failures were never reproduced, so the short read is the likely cause, not a proven one.

**Still varying: io (disk).** Its 60 s capture differs only in the phase of an animated element (a few frames). Likely cause: disk loading time. If AmiMSX's disk routines wait on real AmigaDOS reads while MSX frames keep counting, the load time varies with host disk speed and shifts everything after it. That also fits io's earlier variation at its 20 s logo transition. Low priority; marked unstable in the baseline.

## Lilly's Saga: save-slot menu text as solid blocks, Smooth display off (open, 14 Oct 2026; diagnosis 15 Oct)

- **Seen:** PiStorm A1200, release candidate 188a9a0, Lilly's Saga reloaded with Smooth display off. The SELECT SLOT boxes show '(LOCKED)' and 'NEW!' with letters drawn as solid blocks. The same symptom was seen on BigMig before 76a3bed. With Smooth display on, the PiStorm shows the menu correctly.
- **What draws it:** the glyphs are drawn once with VDP commands (LMMM with TIMP and TXOR, page 3 to page 2) in SCREEN 5, not with the SCREEN 4 tile cache (Fable, openMSX log).
- **Already tried:** BBUSY dummy reads before every blitter wait (8af1d95).
- **Reproduced in openMSX (15 Oct, agents/lilly):** the menu only exists with cartridge SRAM: run `openmsx -machine AmiMSX_MSX2_Disk -cart M_Lilly_A16.rom -romtype ASCII16SRAM8` (plain ASCII16, as tests/titles.csv has it, goes from the title straight into the game, which is why earlier logs never showed the menu). Space at 14 s (logo) and 20 s (PLAY) reaches SELECT SLOT at 22.5 s. Facts from the log:
  - The game writes MSX-Music from 6.3 s (title music), long before the menu, so FmUsed is set and with the release build Smooth display on or off makes no difference to anything that runs in SCREEN 5 (DbPre only runs in SCREEN 4; SprWaitSw and FMXFast are off/forced for an FM game or a 68040). The 'correct with Smooth display on' observation is therefore most likely a race that sometimes fails, not a state difference: re-test both settings several times.
  - The menu is drawn in SCREEN 5 with the display off (R#1 BL=0 from 21.74 to 22.54 s): 204 commands in 4 MSX frames (f953-956), 50-70 per frame. The boxes are LMMV fills (CLR $F, white) and 44-wide LMMM copies from page 2 (y 526); the glyphs are 5-6 wide LMMM copies from the font at page 3 (y 776-808) into the boxes (page 2 y 530-683, page 3 y 824-866). White glyphs on white boxes give black letters, so the text uses TXOR (and TIMP for the icons).
  - A solid black cell is what TXOR produces when the source read is all ones (box XOR box), or when the blit for that cell runs twice with different pointers. It is not what a wrong transparency mask gives: with TXOR the mask is irrelevant (minterm $5A ignores the A channel), and a wrong mask with TIMP would leave the box colour, not a block.
- **Code path reviewed (AmiMSX_Main_v3.1.asm TIMPES/COPIA):** every BLTSIZE in the chain is followed by a dummy BBUSY read and a wait (TIMPOR, ESPBLTMQB), including the last plane, so a command handler returns with the blitter idle and no CPU/blitter VRAM race follows it. The remaining fast-CPU hazard is the BBUSY read right after BLTSIZE itself: if the host posts the BLTSIZE write (Emu68 write buffer, TG68K bus) and the DMACONR read overtakes it, the wait loop sees idle once too early and the next plane's BLTxPT/BLTCON writes land in a blit that has just started: that blit then reads or writes the wrong plane (the destination instead of the font gives exactly a black cell with TXOR). A second read does not help if both overtake the write.
- **Caution on the theory (peer review, 15 Oct):** 8af1d95 already put a dummy BBUSY read before every wait. On a host whose reads drain the posted-write queue that read orders the BLTSIZE write, so the theory implies the host lets reads overtake writes to the same chip bus. The measure-build counter in step (2) (idle on the first read right after BLTSIZE, busy on a later one) has to demonstrate that before any wait-loop change: keep (2) ahead of (3).
- **Plan (needs the PiStorm):** (1) run tools/make_cmd_test.py's ROM (LMMC/HMMM, IMP and TIMP) and a variant with LMMM TXOR 5x8 glyphs drawn with the display off; (2) a measure build that counts, in ESPBLTMQB/TIMPB, how often BBUSY reads idle on the first read right after BLTSIZE and then busy on a later read (the inverse order proves the posted write); (3) if proven, the general fix is one wait that is immune to it: after BLTSIZE read a chip register whose value the write must have changed (e.g. read BLTSIZE's effect through DMACONR only after a read of a register that forces the write to complete on that host), or wait for BBUSY to be seen set before testing for clear, bounded by a short count for blits that finish before the CPU can see them.

## CD32-style pad: direction and fire not together (fix to re-test with the 4.1.1 menu option)

- **Seen:** PiStorm A1200 with a KTRL CD32 pad in the joystick port. In Pampas & Selene you can't move left or right and jump at the same time. It wasn't noticed on BigMig (different controller set-up).
- **To check:** AmiMSX's joystick read (LEEJOY, TesteaJoyRut). It reads port 2 through JOY1DAT and the fire button through CIA-A $BFE001 bit 7, plus POTGO for the second button. A CD32 pad answers the CD32 protocol (button shift register clocked through POTGO/CIA). If AmiMSX writes POTGO ($DFF034 = $FF00) every read, the pad may switch modes and drop either the direction or the button. Also check which MSX key or trigger Pampas & Selene uses to jump: trigger A, trigger B, the space key or Up (then it is about diagonals, not buttons), and whether a plain Amiga joystick behaves the same. Note: $FF00 in POTGO drives pins 5 and 9 high, which is the state that keeps a CD32 pad in plain joystick mode, so the POTGO theory is weak; change the read only with a pad to test against.
- **Checked (cd32, 15 Oct 2026):** the plain read can't drop a direction with a button: the directions come from JOY1DAT and the fire from CIA-A PRA bit 7 in the same pass, once a frame, with nothing conditional between them (LEEJOY builds bits 0-3, pins 6 and 9 add bits 4-5, then NOT.B). The two POTGO writes are $FF00 (START bit 0 = 0, so the pot counters never run and pin 5 stays high) and can't switch a CD32 pad's mode. So if the pad loses a direction while red is held, it is the pad's own plain-mode behaviour (the KTRL is a microcontroller, not a 4021 pass-through), which AmiMSX can't see from the plain read.
- **Done (branch agents/cd32, reviewed on agents/cd32-r2):** TesteaJoyRut now reads the joystick port with the CD32 protocol when a pad answers (see the backlog entry below), so the pad runs in the mode it is built for and its red button comes in through the shift register, not pin 6. Not verified on a real pad yet. Needs the tester's re-test with the KTRL on Pampas & Selene (and which input jumps: trigger A, Space or Up).
- **4.1.1 (agents411/cd32, 18 Oct 2026):** the detection is gone; set Options > JoyPort 2 (Joystick) Pad > CD32 pad and the port is read with the CD32 protocol every frame, forced. Re-test with that setting.

## Lilly's Saga: occasional music slow-down with Smooth display (fix implemented 15 Oct 2026, agents/lilly: DbCommitF; WinUAE 030 only, PiStorm test pending)

- **Seen:** PiStorm A1200, PiStorm preset (60 Hz, Smooth display). The picture and sound are good, but the music slows now and then.
- **Status (15 Oct):** for Lilly's Saga itself 4.0 already switches Smooth display off once the game writes MSX-Music (FmUsed, 91a35e9; Lilly's title music starts at 6.3 s), so the slow-down no longer reaches it. The cost was general, though: any SCREEN 4 game with Smooth display on (PSG/SCC games: Space Manbow, Chikubi Ninja...) lost a whole Amiga frame of MSX time per late frame, because DbPre waits for the VBlank after the last commit before it may draw. Fix 1 below is implemented as DbCommitF (AmiMSX_Dbuf_v4.asm): a frame is dropped when two or more VBlanks have passed since the last commit (its picture would stay two frames anyway) and the beam is still before the $FC tick (the next MSX frame can be drawn before it); the next MSX frame is drawn over it in the same back buffer, so there is no VBlank wait, no catch-up copy (DbRowsAcc carries the rows to the commit after), the dropped frame's per-line copper list and sprite overlay buffer are rebuilt (DbSwapLines undone, SprBufB toggled back, SprSwV reset). A skip is never followed by a skip (no stall when every frame is late), Workbench mode never skips, and key-script SNAPs commit unconditionally. The dropped patch in build/dropped (FpsCred: run late MSX frames at once, plus JR $ idle-loop shortcut) was a different idea; it changed the MSX frame cadence itself and is not needed with this.
- **Tested (WinUAE 030, cycle-exact, so every SCREEN 4 frame is late and the skip path runs constantly):** regress ids 100_ChikubiNinja, R2K_SpaceManbow, R2_BunGaRua with `--opt dbuf=1`, master build and this one: all 9 captures match the baselines (runs lillyA_dbuf, lillyB_dbuf). Wall-clock shots (batch_test, no SNAP) of Space Manbow on the same config: the master build reaches score 600 at 30 s, this build 800 (the MSX runs faster, as the dropped frames intend); the picture is intact at 31-39 and 43-45 s, and the black shot at 41 s is the game's own blank on losing a ship (lives 02 before, 01 after). The first build of this change toggled SprBufB with BCHG (wrong for a 0/FFh flag, fixed with NOT.B in 8b595eb); the regress run with the fixed binary (lillyB2_dbuf) and a longer shot series were started but not finished when the session ended: the lead should rerun `python tools/regress.py ids:100_ChikubiNinja,R2K_SpaceManbow,R2_BunGaRua --exe AmiMSX_lilly_r2 --opt dbuf=1` (build/AmiMSX_lilly_r2 is the agents/lilly-r2 binary) and look at a wall-clock series of a sprite-heavy SCREEN 4 title with dbuf on, on the 030 config, for sprite tearing. Peer review (agents/lilly-r2, 6c6ffae): the first double-buffered frame (DbPostF1, shown directly) now clears SprDrawn, so a skip can never give back the overlay buffer that frame drew; the r2 binary could not be regress-tested either (the WinUAE lock stayed held by a force-ended session for 40 minutes with no WinUAE running), so the 9/9 result above still belongs to the BCHG build only.
- **Not tested:** real fast hardware (PiStorm/BigMig), where skips should be rare (seam frames). The PERF build does not count skips; DbSkips/DbCommits are plain counters in AmiMSX_Dbuf_v4.asm for a measure build.
- **Analysis (Fable, openMSX profile; build/lilly_slow/):**
  - **The game's load:** it rewrites the whole name table each frame and flips pages, with a HUD table split at line 174.
  - **Seam frames:** walking, every 4th frame the column shift changes 171-186 tile pairs. Each pair is one blitter copy, about 110-120 lines on the blitter.
  - **The next frame:** DbCatch copies 18-22 changed rows, about 130 lines.
  - **Result:** those two frames land at 200-250 of the 252 lines available, so some are late.
  - **Why one late frame costs a whole Amiga frame:** the commit only takes effect at the next VBlank, and DbPre waits for it before drawing. The game's VBlank music driver then ticks once in two Amiga frames, which is the tempo drop. DbLineSafe and a third per-line list wouldn't change this.
- **Fixes (exact emulation):**
  1. **Skip-commit catch-up:** when a frame overran, keep drawing the next MSX frame into the same back buffer and commit that one. The display drops a frame instead of repeating one, and the emulation holds 60 fps.
  2. **Make seam frames fit:** do the DbCatch copy and the tile path with the CPU from fast-RAM shadows on 040/060/PiStorm, and overlap CPU-only work with DbCatch.
  3. **Room loads:** a long-write pattern-cache layout.
- **Quick check on hardware:** play the same stretch with Smooth display off. If the music no longer slows, the commit wait is confirmed and fix 1 is the one to do.
- **Diagnostics for the Measure build:**
  - late-frame count;
  - lines waited in DbPre and DbLineSafe;
  - maximum frame length;
  - DbCatch rows and tile blits per window.

## Gradius III Legends: scenery grows from the left (diagnosed 15 Oct 2026: needs the V9958 R#26 coarse scroll, phase 2)

If a pad needs pin 5 low for longer than the ~300 us wait, the read gives all 1s (released) and the pad still works as a two-button joystick through the plain read.

- **Why:** testers use CD32-style pads, and two problems are open with one (direction plus fire in Pampas & Selene; the second button in Gradius 2). AmiMSX reads them as plain two-button joysticks (pins 6 and 9).
- **Plan:** read the pad with the CD32 protocol: pin 5 low (POTGO) to latch, then clock pin 6 (CIA-A DDR and PRA) and read the 7 buttons from pin 9: blue, red, yellow, green, right shoulder, left shoulder, play. AmiMSX takes over the hardware, so it can't use lowlevel.library while the MSX runs. Detect the pad at start (the 8th and 9th bits read back as 1, then 0) and fall back to the plain read without it.
- **Mapping:** red = MSX trigger A, blue = trigger B. Yellow, green, the shoulders and play are useful for keys: Space, M, F1 (pause), F5, and Esc/HELP for the menu. Choose them per game (per-game settings) or with a small menu table.
- **Check:** timing on fast CPUs (PiStorm, BigMig 68040/060): wait between clock edges by reading a CIA register, not with CPU loops. Also check the KTRL's own notes (button remapping: hold SELECT, press the button, then its target; settings reset at power on).
- **Implemented (cd32, 15 Oct 2026):** in TesteaJoyRut (AmiMSX_Main_v3.1.asm, after the plain port-2 read, label CD32Read), joystick port only:
  - First CIA-A PRA bit 7 set and DDRA bit 7 set (pin 6 an output, driven high), then POTGO = $6F00 (OUTRX=1, DATRX=0: pin 5 low = latch; pin 9 an input, OUTRY=0, since the pad drives it; port A's pins high as before), then 200 CIA reads (~300 us, 4-5 lines) for pin 5 to fall: the pot capacitor (47 nF) sits on it, and WinUAE models the discharge as 160/511 per line with the pad switching to CD32 mode below 100, i.e. after 3 lines. Pin 6 goes high before pin 5 falls (review, cd32-r2): with the red button held, the pad pulls pin 6 low in plain mode, and if the Amiga only drove it high after the pad had entered shift mode, that rise would be a clock edge for the pad's 4021 (parallel load while pin 5 is high, shift on the rising edge once it is low) and shift the register one bit early: the ID would land in bits 6/7, the check would fail and the pad would drop out whenever red was held. With the line held high first nothing can move while the pad switches modes; this is the order lowlevel.library and the CD32 use. WinUAE can't show the difference (an output overrides its emulated button and its DDR-change path doesn't clock), and the KTRL's internals are unknown, so the order doesn't rely on either.
  - 9 bits: read POTGOR bit 14 (pin 9), then pin 6 low, three CIA reads, pin 6 high, three CIA reads. Both edges happen between reads, so the shift (rising edge on a real 4021; WinUAE shifts on the falling edge) happens exactly once per bit either way. A CIA access takes an E cycle (~1.4 us) on any CPU, so the pulses are ~4 us per half on a 68030 or a PiStorm alike; the whole read is ~100 us a frame.
  - Then POTGO = $FF00 (plain mode again, as the pin-6 and pin-9 reads expect next frame; a clock edge is ignored in that mode) and DDRA bit 7 cleared.
  - Detection: bit 7 = 1 and bit 8 = 0 (CD32Pad). A plain joystick gives the same level on all nine (pin 9 holds its charge or the second button grounds it) and fails. A detected pad is read every frame; otherwise the port is probed every 16 frames (CD32Cnt), so a plain joystick's fire line is driven high only ~400 us every 320 ms (the pin-5 wait plus the clocking; it is what a CD32 or lowlevel.library does to any joystick every frame, so it is within the port's design; the probe comes after the frame's plain fire read, which it can't disturb). When a detected pad fails a read (review, cd32-r2), the port is probed on each of the next 8 frames (CD32Try) instead of waiting up to 16, and while those retries run the pad's buttons are taken as last frame's (CD32Old), so a one-frame miss (timing glitch, cable noise) changes nothing on the MSX side; after 8 misses the pad counts as gone, its keys are released and the 16-frame probe resumes.
  - Mapping: red = trigger A (bit 4), blue = trigger B (bit 5), ORed into the plain read's bits (a pad in plain mode shows red on pin 6 and blue on pin 9 anyway). Yellow = Space (row 8 bit 0), green = M (row 4 bit 2), play = F1 (row 6 bit 5): the CD32KEY macro presses the matrix key on the button's press and releases it on its release (CD32Old keeps last frame's buttons), so a key held on the keyboard is only released if the same pad button is released at that moment. Shoulders unmapped. If the pad stops answering, its keys are released (D2 = $FF).
  - Menu and prefs unchanged; port 1 (mouse port) keeps the plain read. No lowlevel.library (AmiMSX owns the hardware).
- **Tested (WinUAE; tests only that the probe leaves an idle port alone, nothing about the pad protocol):** tests/jtest.asm (sjasmplus; tests/jtest.rom, also in run/Roms) shows PSG R#14 of both joysticks, keyboard rows 4/6/7/8/10 and a frame counter in SCREEN 0. A test build (`vasm ... -DCD32TEST=1`, build/AmiMSX_cd32t) dumps the raw pad bits 0-7 into matrix row 10 and bit 8 into row 7 bit 0, presses F5 (row 7 bit 1) while a pad is detected and ESC (row 7 bit 2) once the probe has run. Runs: `batch_test.ps1 -Exe AmiMSX_cd32t -Config AmiMSX-cd32pad.uae -Roms jtest.rom -Shots 18,22` (030 config + `joyport1=kbd1`, `joyport1mode=cd32joy`, `joyport1autofire=always`; no key script, so the host joystick is live) and the same with `AmiMSX-cd32plain.uae` (`joyport1mode=joy`).
  - Results: the ROM runs under the new build, the probe runs (ESC marker), the plain read is unchanged (all released, nothing spurious in either config), and the MSX sees nothing wrong from the extra pin-5/pin-6 traffic. But the emulated pad never answered: all nine bits read 1 in the CD32 config, as in the plain one, and WinUAE's "always" autofire on the fire button never showed either (8 captures), so the keyboard-layout port mapping does not seem to be live in the harness run (WinUAE 's `cd32_pad_enabled` is only set when a CD32 button event is mapped on an active input device, and the harness starts WinUAE uncaptured with no host joystick). A first attempt with custom `input.1.keyboard.0.button` lines and `input.config=1` was no better. So the protocol is verified against WinUAE's source (inputdevice.cpp: `cd32padmode` = pin-5 cap <= 100, shift on the falling edge of pin 6 while it is an output, pin 9 = shifter bit, 0 at shifter 0), not against its running emulation.
  - What these runs do and don't show (review, cd32-r2): JOY1/JOY2 read $FF in every capture and the `joyport1autofire=always` fire never showed, so the keyboard-layout joystick was not active in WinUAE at all. The captures therefore prove only that the new code boots, runs its probe and leaves an idle port untouched; they are no evidence for the pad protocol, nor for "no spurious input" with a plain joystick's buttons held during a probe. The feature is hardware-untested. Also, the build/winuae.lock directory the cd32 agent created vanished before it removed it, so another session may have run WinUAE in parallel with these captures; the lead should treat captures from both sessions of that time as suspect. The real test is the tester's KTRL on PiStorm: Gradius 2 power-up on blue, Pampas & Selene direction + jump, and that a plain joystick still works.
- **Risks:** the read costs ~400 us a frame once a pad is detected (200 CIA reads for the pin-5 wait plus ~60 CIA accesses for the clocking; ~2% of a 50 Hz frame on any CPU, measurable on a 68030/50 game already at the limit; once a real pad confirms detection the wait can probably be shortened, WinUAE needs ~3 lines, or the pad left in shift mode between frames with pin 5 pulsed high only to reload) and every 16th frame without one; a plain joystick's fire line is driven high for those ~400 us during a probe (what a CD32 does to any joystick every frame); the KTRL's timing between clock edges is unknown (~4 us per half pulse here, a 4021 needs nanoseconds); if the KTRL needs pin 5 low for longer than 300 us, detection fails and the plain read stays in use (no regression, no gain).

## MSX2+ machine, SCREEN 5 wide layouts: two hardware reports (4.1, A1200), 18 Oct 2026 (branch agents411/cmd)

Both reports are with ROM = MSX2+ only and fine as MSX2, so the suspects were MSX2+ step 2's wide plane layouts (PlMode 1/2: every VRAM line followed by its copy; `AmiMSX_V9958_v4.asm`, Docs/msx2plus_phase2.md 9.1). The command engine's hypothesis (DIX 1 or a fill in the wide layout addressing the wrong rows) did not hold: neither game issues a DIX 1 command, and the engine's half-row walk (CALCULAR/MODODES, both DIY directions, the TABSPR marks, LINE, LMMC) checks out by hand.

- **Pampas & Selene: the character garbled walking right to left (fixed, 2a9fa70).** openMSX (`tools/omsx_vdpio.tcl` + `tools/vdpio_decode.py`, play.keys, 41-45 s, a Tcl wrapper round omsx_vdpio.tcl with play.keys' input from tools/keyscript.py --tcl): the character is **hardware sprites**, not commands. The game keeps two sprite pattern tables, right-facing at 6000h (R#6 = 0Ch) and left-facing at 6800h (R#6 = 0Dh, written the frame it turns), and rewrites the attribute table (128 bytes through port 98h) every frame; its 1357 commands in that window are 8x8 HMMM tile copies and three 16x16 LMMM TIMP item draws, all ARG 00. **Root cause:** `BITPLASPR`/`BITSPRCOL` rebuild a sprite table's VRAM from the planes for every 256-byte block (two VRAM lines) a command flagged in TABSPR. In the wide layouts they stepped over the copy after the block's first line (`PlSkipW` at D7 = 8) but not after its second, so after one rebuilt block every later block of the table was read 32 bytes (layout 1) or 96 (layout 2) early: one VRAM line late, and that wrong line's data replaced the VRAM copy of the table. Right-facing patterns escaped it (their table was rebuilt before the CPU loaded them, or its flags were clear); the left-facing table's blocks were flagged, so its first use rebuilt it wrong and it stayed wrong (the CPU never rewrites patterns). Fix: the readers add `PlSkipW` once more after the block (an add of 0 in the MSX2 layout). **Verified in WinUAE** (AmiMSX-030.uae, prefs `run/cmd411/msx2p.prefs` from `tools/make_msx2p_prefs.py` = the 030 preset with ROM MSX2+, PSG, filter off, passed as `-ExtraArg "P=AmiMSX:cmd411/msx2p.prefs"`; `tests/keys/pampas_lr.keys` = play.keys with SNAPs at 42.5 and 45 s): the unfixed build `build/AmiMSX_cmd411u` shows the scrambled left-facing character at 45 s, the fixed `build/AmiMSX_cmd411` shows it intact. Note the regression baselines never exercise the MSX2+ machine (tools/regress.py has no prefs argument), which is why 4.1 shipped with it.
- **Picture shifted left on MSX2+ (hardware report): not seen in WinUAE.** The fixed MSX2+ capture at 45 s and the MSX2 baseline capture of the same frame differ only inside the character (an animation phase): the background and the HUD are pixel-identical, so the 32-bit fetch (`FMODE $000D`, W5FETCH 36, `Adj5Calc` D = 32 at R#26 = 0) puts the picture where the 64-bit fetch does in WinUAE. ## Uridium 2 (M_Uridium2_SCC): splash screen wrong (fixed 19 Oct 2026, branch agents412/urid)

- **Cause and fix (228226d, Docs/agent_notes/urid.md):** not the renderer: the picture was streamed (OTIR) to VRAM C08Eh instead of 0000h. The game waits for VR in S#2, then writes its registers in port-99 pairs with interrupts enabled. AmiMSX only took a pending interrupt at a line end, so the VBlank interrupt (requested with VR at line 212) landed between the two bytes of the "00 87" pair; the handler's S#0 read reset the latch and every later byte was mis-paired ((8E,00) became the address 008Eh, R#14 = 0 was never written). A Z80 accepts a pending interrupt right after the instruction following EI, i.e. at the poll routine's EI/RET, before any pair. `EI` now forces the interrupt check after the next instruction (EISave/EIForce, MiraInterEI). Verified: burst 6-30 s against openMSX (build/bursts/u2fix), the picture whole from 6 to 14 s and play from 16 s. Regression (ids runs u2fix, u2fix2, 10 titles): Snake and Rhino, Metal Gear, Chikubi Ninja, Pampas and Selene unchanged; Uridium 2, Zanac EX, Space Manbow, Nemesis 3, Bun-Ga-Rua and Uridium (MSXdev) changed only in game state (scroll position, sprite positions, a different Uridium 2 attract sequence), no corruption: their baselines need re-accepting with the fix.

URI") along the bottom edge. Identical in 4.1 and 4.1.1, so not a 4.1.1 regression; gameplay from 16 s matches openMSX.

## Gradius 2 enhancement patch (grad2tr) on MSX2+: dot grid on the star field (fixed 19 Oct 2026, agents412/msx2p; A1200 test pending)

- **Seen:** A1200, 4.1 and 4.1.1 builds, ROM = MSX2+: a regular grid of blue dots in rows over the star field; as MSX2 only the normal scattered stars. Reproduced in WinUAE (030 preset, `option machine 2`, 46 s of play.keys: build/g2p/m2).
- **Found:** not the step 2 tile path (at that point the game has SP2 off and R#26 = 0: openMSX C-BIOS_MSX2+_EU logs, build/g2p/omsx), and not VRAM (a STATEDUMP of AmiMSX's VRAM mirror equals openMSX's: 32 scattered star names, the rest $00). The dots are stale images of the star tile $FF at even tile columns and rows (static across captures while the real stars move). PREPARATXT4 marks a tile whose pattern/colour changed by writing its inverted name into the name shadow for the next frame's COPIATXT4; NOT $FF = $00, and the patched game twinkles the star patterns every 4 frames while it moves the stars by names every 16, so a star erased ($FF -> $00) right after a twinkle matched its own mark and was never redrawn. A general latent bug of the deferred mark (any name N replaced by 255 - N); the MSX2 fallback of the game doesn't hit it.
- **Fix:** PRINT4 (and PRINT2) run the name compare again in the same pass when PREPARATXT marked anything, after TRANSBLT updated the cache (`PrepMark`): no mark survives to the next frame. Verified in WinUAE (build/g2p/fix: scattered stars as openMSX). Details: Docs/agent_notes/msx2p.md.
