# AmiMSX regression testing

There are three tiers, run by `tools/regress.py`. Each title runs in WinUAE with its own key script, and the captures are compared pixel for pixel with an accepted baseline.

## Tiers

| Tier | Command | When |
|---|---|---|
| Smoke | `python tools/regress.py smoke` | Every change. 15 titles × 3 captures, about 50 minutes. |
| Feature | `python tools/regress.py feature:<name>` | Changes to one area. For example `feature:cmd:LMMC`, `feature:split:mode` or `feature:mapper:KonamiSCC` runs every title that uses it. |
| Full | `python tools/regress.py full` | Before committing Z80-core, timing or VDP changes, and at milestones. |
| Named | `python tools/regress.py ids:a,b` | Ad hoc checks. |

Each run writes `build/regress/<run>/report.md`. If anything changed it also writes `changed.png`, a side-by-side sheet of baseline and new captures for the changed titles only. To make a run the new baseline, add `--accept` to the run, or use `--accept-run <run> [--ids a,b]` afterwards.

`--calibrate` runs a tier twice: the first run becomes the baseline. Captures that differ between the two runs are stored as unstable (`baseline/<id>/unstable.txt`), and later runs report those as "varies" rather than "changed". After the beam-synced start, most titles are fully repeatable. The exceptions are games that read input AmiMSX takes from the host, such as the mouse.

## Titles and coverage

- **`tests/titles.csv`** lists every title. Columns:
  - the file and its set;
  - the openMSX ROM type;
  - the key script;
  - the WinUAE config (all on `030`, which is cycle-exact);
  - the shot times;
  - the smoke flag, features and notes.
- **`Docs/coverage.md`** is generated by `tools/coverage.py` from an openMSX scan (`tools/scan_titles.py` with `tools/omsx_featurescan.tcl`). It records what each title actually uses:
  - screen modes, sprite mode and line interrupts;
  - mid-frame splits (mode, tables, scroll, adjust, sprites on/off, border);
  - palette writes and VDP commands;
  - the mapper.
- **The smoke set** is the canaries (titles that broke before), plus a greedy cover of every feature. Rerun the scan and `tools/coverage.py` when titles are added.

## Key scripts (`tests/keys/*.keys`)

Scripted MSX keyboard input is injected inside AmiMSX through the keyboard matrix, so it doesn't depend on window focus. One action per line:

```
14s   SPACE 5 every 100 until 30s      # Space taps past the title
32s   LEFT  5                          # hold LEFT for 5 frames
48s   LEFT  400                        # walk left for 8 s
50s   SPACE 5 every 25 until 70s       # punch
30s   SNAP                             # capture this exact MSX frame
option sprites 1                       # AmiMSX: sprites drawn every frame
include play.keys
```

- **Times** are MSX frames (50 Hz) from power on, or seconds with an `s` suffix.
- **Keys:**
  - cursor keys: `LEFT`, `RIGHT`, `UP`, `DOWN`;
  - action keys: `SPACE`, `RETURN`, `ESC`, `TAB`, `BS`, `SELECT`, `STOP`;
  - `F1`-`F5`, `SHIFT`, `CTRL`, `GRAPH`, `0`-`9`, `A`-`Z` and punctuation.
- **`SNAP`** makes AmiMSX hold the finished frame with the Amiga power LED on, and the harness captures it when the LED shows in WinUAE's status bar. Captures are therefore exact MSX frames, not wall-clock moments.
- **`tools/keyscript.py`** turns a script into AmiMSX's binary format (passed as the CLI hook's second argument) or into an openMSX Tcl script, where SNAP becomes a screenshot. The same file drives both emulators.
- **Repeatability.** A scripted run gives the same MSX state at the same frame every time; VRAM was compared byte for byte at frame 1500 across two runs. Several things make that true:
  - **Start:** the MSX starts at the top of an Amiga frame.
  - **Host input is ignored:** the Amiga keyboard, mouse and joysticks are blocked (moving the mouse over WinUAE used to reach MSX joystick 2).
  - **Sprites:** `option sprites 1` makes AmiMSX draw sprites every frame.
  - **Captures:** the harness only arms after the Workbench boot has lit and then dimmed the LED (it used to capture the boot screen). It keeps re-grabbing while the LED is lit and keeps the last grab: in warp mode WinUAE presents frames to the window only now and then, so an early grab can show an older frame.
  - **One SNAP per run:** `tools/regress.py` makes one run per capture. That costs time but keeps every capture independent.

|---|---|---|
| BUN-GA-RUA | `bungarua.keys` | LEFT (English) then Space on the title; walk left to meet the enemies |

| Everything else | `play.keys` | Space through the menus, then right, left, up, down and fire |

## Lower-level tools

- **`winuae/batch_test.ps1`:** one or more titles. Options:
  - `-Keys file.keys` for scripted input; SNAP lines are captured automatically;
  - `-Shots` for wall-clock captures;
  - `-WaitFile perf.bin` for PERF builds.
- **`winuae/strips.ps1`:** film strips. Build sheets with `tools/strip_sheet.py`.
- **`winuae/perf_ab.ps1`:** PERF A/B on several configs. Decode with `tools/read_perf.py` and `tools/read_prof.py`.
